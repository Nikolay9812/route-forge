# Route Forge

Expo React Native app for courier companies. Couriers log their daily work (hours, packages, kilometers, car). Dispatchers approve it. Owners see the whole firm, including salaries. One app serves many logistics firms: Ivanov Transport is the first, and others can join later without code changes.

This file is the project's memory: it holds every decision that is still true. Plans in `prompts/` are history.

## Expo

- Expo ships breaking changes every SDK release, so don't trust memory. Before touching an Expo, EAS, or React Native API, check the `expo` major version in `package.json` and read `https://docs.expo.dev/versions/v<major>.0.0/`. For anything else, start from https://docs.expo.dev/llms.txt and follow its links.
- Routes live in `src/app/`: every file is a screen and `_layout.tsx` files define navigators. API routes are `src/app/api/*+api.ts`. Keep components, hooks, and utils outside `src/app/`.
- `ios/` and `android/` are generated. Never create or edit them by hand; configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, switch to a development build (`npx expo run:ios`).
- Styling uses NativeWind v5 (pinned RC) with Tailwind v4: `className` on React Native components. `src/global.css` is the only stylesheet and is imported in the root layout. Use `StyleSheet` only for what a utility can't express. Keep `nativewind`, `react-native-css`, `tailwindcss`, `@tailwindcss/postcss`, and `lightningcss` (also forced via `overrides`) pinned, and upgrade them together using the NativeWind v5 docs. `metro.config.js` lets `node_modules` import the real `react-native` (NativeWind's re-export drops `AssetRegistry`, which breaks fonts and icons on Android); keep that when touching Metro config.
- Design tokens live only in `src/global.css` (`@theme`, with dark values under `prefers-color-scheme`). Tailwind's default palette, type scale, radii, and shadows are removed, so use Route Forge tokens (`bg-canvas`, `text-ink`, `rounded-md`, `h-button`). Spacing is a 4px step (`p-4` = 16). Line-height tokens are unitless ratios (`calc(22 / 15)`), never px: on Android NativeWind reads a px line height as a multiplier and text disappears. Dark mode follows the system until the user picks one with the moon/sun button on Profile (`useToggleColorScheme` in `src/theme/color-scheme.ts`: `Appearance.setColorScheme`, saved in SecureStore as `colorScheme` and restored before the first render; not on web). In JS, read colors with `useThemeColor` from `@/theme`, never hex.
- Hours always read `7:15 h` (`format.hours`; bare `clock()` only in tiles whose caption already says hours), never decimals.
- Text goes through `ThemedText` with a `variant` and optional `color` token, never `font-bold`, `text-[n]`, or a color className (two color classes resolve by stylesheet order). Fonts: Plus Jakarta Sans for EN and DE, Manrope for BG (Plus Jakarta Sans has no Cyrillic), static weights in `assets/fonts/` loaded with `useFonts` in the root layout. `FontScriptProvider` picks the family.
- Icons: `expo-symbols` through `<Icon name color>`, with names from the registry in `src/components/icons.ts`. Add new icons there with an iOS and an Android name.
- Shared primitives live in `src/components/` (button, icon-button, text-field, chip, segmented-control, stepper, toggle, tag, alert, surface, pressable-scale, action-sheet). Check them before building a new control. Choices go in `ActionSheet` (themed, over the `scrim` token), never `Alert.alert` with buttons: Android's system dialog ignores the app's colors. Tailwind v4 only emits theme colors some className uses, so a token read only through `useThemeColor` comes back empty: use an existing one. Their `className` is for layout only, and they take all text as props. `/design-system` is a dev-only showcase of all of them.
- On web, routes are server-rendered, so anything that differs between server and browser (locale, color scheme, `window`) must not change the first render.
- i18n: `expo-localization` + `i18n-js`. Strings live in `src/i18n/locales/{en,bg,de}.json` (en is the source of key types) and are read with `useTranslation()` from `@/i18n`. `useLanguage()` gives the app language (en on the server's first render) and also picks the font script via `fontScriptFor`.
- Stock photos (Unsplash) are downloaded into `assets/images/<feature>/` with a `CREDITS.md`, never hotlinked. App identity: "Route Forge", ID `com.routeforge.app` (iOS and Android; fixed once released), icons are PNGs in `assets/images/` (amber route on `ink`; iOS light/dark/tinted, Android adaptive + monochrome), splash on `canvas` light/dark. Native permission prompts: image-picker plugin (EN) and `src/i18n/native/{bg,de}.json` (iOS); update both with any new camera or photo use. Android storage permissions stay (the picker needs them below Android 13); block only unused ones in `android.blockedPermissions`.
- Routing by auth: `/` redirects by Clerk auth state. Signed-out users get onboarding and `(auth)`, signed-in users get `(app)`, guarded with `Stack.Protected` in the root layout. The splash stays up until fonts and Clerk are loaded.
- `(app)` is `NativeTabs` from `expo-router/native-tabs`, the platform's own tab bar. Tabs depend on the role: couriers get Home, Shifts, Pay, Profile; dispatchers and owners get Approvals, Team, Profile (the others are `hidden`, which also blocks navigating to them). Mechanics get Cars and Profile. `/` redirects reviewers to `/approvals`, mechanics to `/cars`, everyone else to `/home`. Tab icons come from the icon registry (`sf` + `md`), labels from translations, colors from `useThemeColor`.
- Motion: Reanimated only (never core `Animated`), animating `transform` and `opacity` only, following the `expo-animation` skill. Tab switches and screen transitions stay native. Press feedback on cards and round buttons is `PressableScale` (scale 0.97, 120 ms); full-width rows highlight their background instead. Content fades up only when it first arrives, never on refresh or tab return. Every animation handles reduced motion (fade only, no movement). Curve: `cubicBezier(0.23, 1, 0.32, 1)` in CSS transitions, `Easing.bezier(0.23, 1, 0.32, 1)` in builders. `Animated.View` takes no `className`: put animation in `style` (typed `CSSStyle`) and visuals on an inner `View`.

## Who owns what

Each tool has one job. Ask before moving a responsibility to a different tool.

- **Auth, firms, and roles:** Clerk is the source of truth for sign-in and firm membership. Each firm is a Clerk Organization. The app role in a firm (`owner`, `dispatcher`, `courier`, `mechanic`) lives in Neon `firm_members`, never in Clerk, and access needs both a role row and the verified session token's active org. The app keeps its own custom auth screens. They import auth only from `src/auth/`, which adapts `@clerk/expo`'s current custom-flow API (`{ error }` results, `finalize()`) and maps Clerk error codes to translation keys, so screens never show raw Clerk messages. Sessions persist through Clerk's `tokenCache` (`expo-secure-store`). Change Clerk instance settings through the Clerk MCP server (`.mcp.json`) or the Clerk CLI (in Git Bash prefix `clerk api` calls with `MSYS_NO_PATHCONV=1`), and use the Clerk skills for current Expo patterns.
- **Organizations:** only Clerk's free built-in roles: `org:admin` for owners, `org:member` for everyone else (they mirror ownership; nothing reads them for permissions). Free plan: 20 members per firm (instance and each firm's `max_allowed_memberships`); custom roles or more members need Clerk's B2B add-on, which needs no code change. Organization selection isn't forced. A member with no row gets one on first sight (`roleOf` in `src/server/members.ts`): `org:admin` → owner (a firm's creator), else the invitation's role (invites carry `publicMetadata.role`, which Clerk copies onto the membership), else courier. Owners come from the creator, the seed or `npm run role:owner -- <email> "<firm>" add|remove` (row + Clerk role; never the last owner), never the app. Owners manage people in Profile → People (`usePeople()` from `src/people/`, `src/server/people.ts` over Clerk's backend API): invite couriers, dispatchers and mechanics by email (Clerk sends it; it's accepted on `NoFirm`; Clerk silently replaces a duplicate pending invite, so the server checks first), revoke pending invites, switch between courier, dispatcher and mechanic, pick a dispatcher's active depots (`dispatcher_depots`), and remove members. Owners can't be changed in the app (the API answers `notEditable`). A role change clears the user's depot rows; removing deletes only the membership, role and depot rows, so shifts, pay and documents stay and Team/Couriers rows show "Former". Someone removed in the Clerk dashboard loses access within about a minute (the token drops the firm); People and a new invite to their email delete their stale rows (no webhooks). The server applies role changes at once; the person's app shows them when it next comes to the foreground. `useFirm()` in `src/auth/` (shared by `FirmProvider` in the root layout) gets the role from `GET /api/me` (spinner, then an error with Retry; nothing stored on the device) and activates the first membership; with none, `(app)` shows `NoFirm` with pending invitations to accept. Test firms: Ivanov Transport and Test Firm B, with `+clerk_test` users courier.a, courier.c, dispatcher, owner, mechanic (Ivanov) and courier.b (Firm B).
- **Data:** Neon Postgres holds depots, cars, shifts, pay rates, courier documents, firm settings and the service log. Only API routes reach it, through `DATABASE_URL`. The app never talks to the database directly. Access goes through Drizzle ORM over Neon's HTTP driver. Tables live in `src/db/schema.ts` (camelCase in TS, snake_case columns) and the `db` client in `src/db/index.ts`, imported only by API routes and scripts. Atomic multi-statement writes use `db.batch`. `npm run db:push` uses the direct `DATABASE_URL_UNPOOLED`. Tables: `firm_settings` (currency, timezone; the name comes from Clerk), `firm_members` (one role per firm and user), `firm_rules` (dated break and Spesen rules, like pay rates), `depots`, `cars` (with the papers: VIN, TÜV, insurance, service), `pay_rates` (`user_id` null = the firm default), `shifts` (one per courier per day), `courier_details` (one row per courier per firm, typed nullable columns), `document_photos` (one per courier, section and slot; only the R2 object key), `shift_photos` (one per shift and slot; only the R2 object key), `car_photos` (one per car and slot, owner-only; only the R2 object key), `car_notes` (the service log) and `car_note_photos` (up to 3 per note; only the R2 object key). When `db:push` can't run because it asks interactively (e.g. whether a table was renamed), push in two passes: without the new table, then with it. drizzle-kit re-detects `pay_rates`' `NULLS NOT DISTINCT` unique on every push and asks whether to truncate when the table has rows: empty `pay_rates` first, push, then `db:seed`. `.env.local` points at the Neon `dev` branch (main's URLs are kept as comments); the seed data lives there.
- **Files:** document and shift photos live in a private Cloudflare R2 bucket per environment (dev: `route-forge-documents-dev`, EEUR; production gets its own). Only API routes and scripts reach it, through `src/server/storage.ts` (`aws4fetch` over R2's S3 API, `R2_*` env; no `@/` imports so scripts can use it). Postgres keeps only the object key. The app uploads straight to R2 with a 5-minute presigned PUT (Content-Type signed in) and shows photos through 1-hour presigned GET URLs. Keys are `firms/{firmId}/couriers/{userId}/{section}/{slot}/{uuid}` (shift photos: `…/{userId}/shifts/{shiftId}/{slot}/{uuid}`; car photos: `firms/{firmId}/cars/{carId}/{slot}/{uuid}`; note photos: `…/cars/{carId}/notes/{noteId}/{slot}/{uuid}`), made by the server only. Photo rules (types, 10 MB, slots, key checks) live in `src/domain/photos.ts`; the app uploads through `uploadPhoto()` in `src/photos/upload.ts`. Nothing is public. `CLOUDFLARE_API_TOKEN` is for bucket management from local scripts only. `db:seed` deletes each seeded firm's `firms/{firmId}/` objects.
- **Business logic** (permissions, approvals, salary math): code in API routes and shared utils, never in the client alone. Shared domain code lives in `src/domain/` (types, `shift.ts` rules and input parsing, `salary.ts`, `dates.ts`, `calendar.ts` Monday-first month grid and month stats): pure, no React, only type imports between files, so API routes, the app and Node scripts (`node --no-warnings scripts/check-salary.mjs`) all run it.
- **API:** routes call helpers in `src/server/` (`courierContext` / `requireCourier`: Clerk session via `@clerk/backend` → active org → role from `firm_members`, then firm settings and the firm's today; `GET /api/me` answers `{ firmId, role }`) before any work, and return `{ error: code }` (`ApiErrorCode` in `src/domain/types.ts`) without details. Every shift query goes through `mine()` (firm + user). Every `Shift` carries `minutes` (shift time), `breakMinutes` and `workedMinutes` (the break comes from `breakMinutesSql` in `src/server/work-rules.ts`, the SQL twin of `breakFor`), `photoCount` (expected vehicle check photos taken) and `car.vin`; the `buses` pick list never carries VINs; `GET /api/shifts/today` and `GET /api/shifts/:id` also answer `photos` with signed URLs, lists never do. Courier routes: `GET|POST|PATCH /api/shifts/today`, `POST /api/shifts/today/submit`, `GET|PATCH /api/shifts/:id` and `POST /api/shifts/:id/submit` (own shift; fix and resubmit when rejected, never its times), `POST|PUT|DELETE /api/shifts/:id/photos` (own `draft`/`rejected` shift, else `notEditable`; start `{ slot, contentType }`, keep `{ slot, key }`, remove `?slot=`; answers the shift's photos), `GET /api/home` (today and recent shifts, no pay), `GET /api/calendar?month=YYYY-MM`, `GET /api/pay?month=YYYY-MM` (approved totals, the rates in force that month, the next change for the current month, approved + submitted days with per-day pay for approved ones, and the 5 months before the current one with pay, hours and shift count), `GET|PATCH /api/details` (own documents with signed photo URLs; PATCH `{ section, values }` with every field of one section), `POST|PUT|DELETE /api/details/photos` (start an upload `{ section, slot, contentType }` → `{ key, uploadUrl }`; keep it `{ section, slot, key }`; remove `?section=&slot=`). Reviewer routes (`reviewerContext`: dispatcher or owner, scoped by `inScope()` to the firm and the dispatcher's depots; out of scope answers 404): `GET /api/approvals?view=pending|reviewed` (optional `depotId`, `carId`, `userId`, `photos=missing`, `corrected=1`, `status=approved|rejected` in Reviewed, `sort=date|courier|depot|bus`, parsed by `src/domain/review-filters.ts` and applied inside `inScope()`, so an ID out of scope matches nothing; answers the filtered `total`, the unfiltered `pendingCount` and `options` (depots, couriers, buses of both views)), `GET|POST|PATCH /api/approvals/:id` (detail with pay, history and photos; approve/reject; correct), `GET /api/team` (owners: every courier member plus anyone with shifts; dispatchers: couriers with shifts in their depots; no pay), `GET /api/team/:userId?month=` (that courier's in-scope month). Owner routes (`ownerContext` / `requireOwner`, everyone else gets `role`): `GET /api/firm` (Firm settings view, also before a settings row exists), `PUT /api/firm/settings` `{ currency, timeZone }` (`notEditable` once the firm has shifts), `POST /api/firm/rules`, `PATCH|DELETE /api/firm/rules/:id` (whole rule, upcoming only; all answer the view), `GET /api/people` (members of every role, pending invites, active depots), `POST /api/people/invitations` `{ email, role }` (`exists`, `memberLimit`), `DELETE /api/people/invitations/:id`, `PATCH /api/people/:userId` `{ role }` or `{ depotIds }`, `DELETE /api/people/:userId` (deletes answer the updated list), Garage routes (`garageContext`: mechanic or owner, whole firm): `GET /api/garage` (active cars by depot, warnings, last note day), `GET /api/garage/cars/:id` (an active car's papers and signed talon, its shifts of today and the 6 days before as `{ shiftId, date, courierName, photoCount }` only, latest 5 notes), `GET /api/garage/shifts/:id` (one of those checks with signed photos; else 404), `GET|POST /api/car-notes` (`?carId=&type=&before=` cursor pages of 50; add to an active car), `GET|PATCH|DELETE /api/car-notes/:id`, `POST|PUT|DELETE /api/car-notes/:id/photos` (author within 7 days, like the shift photo calls). `GET /api/fleet` (every depot with its cars, their papers, `odometerKm` and `hasTalon`, archived included, plus the firm's `today`), `POST /api/fleet/depots|cars`, `PATCH /api/fleet/depots/:id|cars/:id` (rename or move, `{ papers }` with all five fields, or `{ archived }` to archive/restore; never delete), `GET /api/fleet/cars/:id` (one car with its signed talon photo), `POST|PUT|DELETE /api/fleet/cars/:id/photos` (talon; like the shift photo calls, answers the car), `GET|POST /api/pay-rates` (firm default and every courier's entries; The app calls them with `useApi()` from `src/api/client.ts` (relative URLs, bearer token; failures become codes, `offline` when no answer).

## Domain

- **Firm:** a tenant (Clerk Organization). It holds its own name, logo, currency, and timezone. The owner sets currency and timezone in Profile → Firm settings (fixed lists in `src/domain/firm.ts`, defaults EUR / Europe/Berlin), locked once the firm has shifts. Never hardcode "Ivanov Transport" or any other firm's details.
- **Depot (station):** belongs to a firm. Couriers and cars are assigned to depots. A dispatcher manages one or more depots.
- **Car:** belongs to a firm and has a plate number and a depot. A shift records which car was driven. Its papers (rules in `src/domain/fleet.ts`, all optional, saved whole by the owner with who and when): VIN (spaces/hyphens dropped, uppercase, 17 of A–Z 0–9 without I, O, Q, no check digit; unique per firm), TÜV/HU due month (stored as that month's last day), insurance expiry, next service date and km, and one talon photo (Zulassungsbescheinigung Teil I; owner-only, replacing or removing deletes the file). `carWarnings`: a date passed or within 30 days, or the odometer (highest end km of submitted/approved shifts) within 1,000 km of the service km. Couriers see only their shift car's VIN; only owners and mechanics see the rest (mechanics read-only).
- **Service log** (`car_notes`, rules in `src/domain/car-notes.ts`): a note on a car has a type (tyres, oil, brakes, inspection, repair, other), the day the work was done (today back to a year, firm days), optional km and text (required for other, up to 1,000), up to 3 photos (camera or library) and who wrote it when. Mechanics and owners add notes to active cars; the author edits or deletes within 7 days of writing (then locked), the owner deletes any. Deleting removes its photos (not salary history). Mechanics see vehicle check photos of the last 7 days with the courier's name only, never shift times, km, packages, status or pay.
- **Managing depots and cars** is owner-only. Depot names are unique per firm ignoring case, plates are stored normalised (trimmed, uppercase, single spaces; letters of any script, digits, `-`, up to 15) and unique per firm. Archived rows keep their name or plate, so restore instead of re-creating. A depot can't be archived while it has active cars, and a car can't be restored or moved into an archived depot. Archiving only hides a row from new picks; shifts keep it.
- **Shift:** one courier, one day, one depot. Records start and finish time, start and end km (driven = end − start), packages loaded, returned, and pickups (Abholung, customer returns), and the car. Delivered is never typed: it is loaded − returned, and returned can't exceed loaded. Status moves `draft → submitted → approved` or `rejected` (reason codes `km`, `packages`, `busOrStation` plus an optional note; wrong times are corrected by the reviewer, not sent back). The courier edits a shift only while it is `draft` or `rejected`. The courier never sets the start time: it is when they tapped Start (`PATCH /api/shifts/today` has no `startedAt`), and a forgotten Start is corrected by a reviewer. Fixing a rejected shift can't change its start or finish time (shown locked; the API answers `invalid`), so resubmitting keeps its times. Dispatchers approve or reject submitted shifts and correct submitted or approved ones (status unchanged). Reviews set `reviewed_at`/`reviewed_by`; each corrected field writes a `shift_changes` row in the same transaction, and the shift shows as "Corrected".
- **Vehicle check photos** belong to a shift (never required, never block anything): bus `front`, `back`, `left`, `right` plus `extra1`, `extra2`, then `logbook`, `mentor` (Mentor app score), `diesel`, `adblue`. 8 are expected; extras never count. Camera only, except Mentor (a screenshot) which also allows the library. The courier adds, replaces and removes them only while the shift is `draft` or `rejected`; reviewers only view. Removing or replacing deletes the file. If the bus changes, the photos stay.
- **Breaks and Spesen** (Firm settings, `firm_rules`, math in `salary.ts`): computed, never stored, from the rule in force on the shift's day (dated like pay rates: upcoming-only edits, past starts after a warning; no rule = no break, no Spesen). A shift over `breakAfterMinutes` (law default 6:00 h) loses `breakMinutes` (30), over `longBreakAfterMinutes` (9:00 h) `longBreakMinutes` (45 total); "over" is strict, no cap. Worked minutes = shift time − break, and all hours and hourly pay use them. Spesen (default €14.00): per approved shift whose shift time, before the break, is over `spesenAfterMinutes` (8:00 h), for every pay type; tax-free, shown apart from salary, never on Team.
- **Salary:** each courier is paid either hourly (approved worked minutes × rate, rounded per shift half up, minor units) or with a day rate (a fixed amount per approved shift, however long), never both. The owner sets a firm default and per-courier overrides. On a given day, the courier's latest own entry on or before it applies, else the firm default's latest; a `firm` entry means "follow the firm default" again. Every entry has a start date (a firm calendar day), so a change never rewrites days before it. Past start dates are allowed after a warning and change approved pay. Only upcoming entries can be edited or cancelled. Every entry records who set it and when. Couriers see only their own rate. Monthly totals are computed from approved shifts only, never stored as fixed numbers. Months are never locked: correcting an approved shift, even in a paid month, updates that month's total. Every correction records who changed what and when.
- **Courier documents:** nine sections (ID card, driving licence, registered address in Germany, Steuer-ID + tax class, social security number, health insurance, Führungszeugnis, bank account, contacts), rules in `src/domain/courier-details.ts`. All optional; they never block shifts. A section is saved whole and is missing, incomplete or complete (photos don't count). Warnings: an ID card or licence expired or expiring within 30 days, a Führungszeugnis older than 3 months. Couriers edit their own, owners see and edit every courier's, dispatchers get nothing. No checked state or change log; the row keeps only who saved last. Personal data: never logged. Photo slots (`sectionPhotos`): ID card and licence front + back, address, tax and health card one each, Führungszeugnis 3 pages; JPEG/PNG/HEIC/WebP up to 10 MB. Replacing or removing a photo deletes the old file and row (photos aren't salary history). The expiry countdown shows every non-zero calendar unit ("Valid for 2 years, 3 months, 5 days", "Expires today", "Expired 4 months ago").

|------------|-------------------------------------------|----------------------------------------------------|

## Rules

- **Tenant isolation:** every firm-owned table has a `firm_id`, and every query filters by it. The firm and role come from the verified Clerk session, never from the request body or URL.
- API routes verify the Clerk session, then check role and depot access, before doing any work. Hiding a button in the UI doesn't count as a permission check.
- SQL always uses parameters. Never build queries by joining strings with user input.
- Schema changes go to the database only with `drizzle-kit push`, from the Drizzle schema in git. Never generate, write, or run migration files (no `drizzle-kit generate` or `migrate`, no migrations folder or migration scripts). Push to a Neon branch first, then to the main branch.
- **Development project:** there is no backwards compatibility and the data is worthless. Prefer data loss: never backfill, migrate, or preserve existing rows, and never spend effort keeping old data working. Every schema change means a clean state.
- Money is stored as integers in minor units (stotinki, cents) with the firm's currency code. Working time is stored in minutes. Never store money in floats.
- Calendar days and months follow the firm's timezone. Store timestamps in UTC.
- Never hard-delete couriers, cars, depots, or shifts that salary history depends on. Archive them instead.
- Salaries are personal data. Never log them, and never return them to roles that can't see them.
- Personal files never go to a public bucket or URL. Signed URLs are short-lived and never logged.
- Secret keys (Clerk secret key, `DATABASE_URL`, `R2_*`, `CLOUDFLARE_API_TOKEN`) never reach the app bundle. Use them only in API routes and local scripts such as seeding. Never put them behind `EXPO_PUBLIC_`, which is bundled into the app. Never commit `.env`. Keep variable names, without values, in `.env.example`.
- Ask before adding a dependency or service. Prefer Expo modules over third-party libraries.
- Whenever you need input from the user, ask through your tool's built-in question panel so they pick from options instead of typing. Give two to four clear options with the recommended one first. Fall back to plain text only if no such panel exists.

## How we build features

For a new feature or a change across several files. Small fixes and questions skip this.

1. **Understand.** Read the code involved. Open an earlier plan only if this feature builds directly on it (pick by file name). Read the current docs pages for the APIs you'll use, and load a matching skill if one exists (e.g. the Expo, Clerk, or Neon skills). Don't write version-specific APIs from memory.
2. **Ask.** If a real decision is unclear (scope, visible behavior, data shape, who may see or change what), ask in the question panel, batching questions into one round and following up only if the answers raise new ones. Pick defaults for the rest and list them. If a decision in this file looks wrong, raise it instead of changing it.
3. **Plan.** Copy `prompts/TEMPLATE.md` to `prompts/NN-feature-name.md` (next number) and fill it in. The plan must be self-contained, so a fresh session can build it from this file plus the plan alone.
4. **IMPORTANT: stop and wait.** Write no app code until the user approves the plan. Ask for approval in the question panel (approve, or request changes). If they request changes, update the plan and ask again. On approval, set `Status: approved`.
5. **Build** step by step, checking each one. If a step turns out wrong, stop and explain instead of redesigning.
6. **Close out.**
   - Run the plan's Verification and give the report described under Reporting.
   - Add a short `## Result` to the plan and set `Status: done`.
   - Update this file: put each lasting decision in the section it belongs to. Replace or remove rules that are no longer true instead of appending. Keep this file under 150 lines.

## Building from designs

Designs are attached in the chat. Screens must match them exactly: layout, spacing, sizes, colors, type, radii, icons, and copy. The design system reference is the Route Forge Design Board (`https://claude.ai/artifact/4x1GGuAYpH6XjXYM3hQ3mu`), with panels numbered 01–15. Its icons are stand-ins; the app uses native symbols.

- Icons, fonts, and brand images come from `assets/` or the chosen icon library, never recreated from a screenshot. Firm logos come from firm settings, not from `assets/`. If an asset is missing, use a marked placeholder and list it.
- Map every color, font, spacing value, and radius to a design-system token. List values with no token in the plan as proposed new tokens instead of hardcoding them. When creating the design system itself, derive the tokens from the designs.
- UI plans describe the design (elements, states, tokens, assets) well enough to build without the image. If building in a new session, ask for the design to be attached again.
- After building, open the screen in the iOS simulator (deep link with `xcrun simctl openurl booted <url>` when it isn't the first screen; the scheme is in `app.json`), take a screenshot (`xcrun simctl io booted screenshot <path>`), and compare it with the design. List every difference, fix, and repeat. Report which values were estimated from an image.

## Reporting

End every piece of work that changes code (features and fixes, not answers to questions) with this report. Use these headings in this order, and leave out any section that would be empty.

- **Done:** one line on the outcome, then the files changed and what changed in each.
- **Verified:** each check with ✅ or ❌ and its evidence (command output, screenshot). List what wasn't checked as ❌ with the reason. Never mark something ✅ without running it.
- **You need to:** numbered actions only the user can take, such as keys, Clerk or Neon dashboard settings, or assets to provide.
- **Test it yourself:** numbered steps to reproduce the result from a fresh start, ending with `Expected:` and what the user should see.
- **Notes:** defaults picked, trade-offs, and anything left for later.
